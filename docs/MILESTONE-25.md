# Milestone 25 — Reject-before-side-effect HTTP and concurrency regression

## Purpose

Ensure authentication/authorization and the strict input contract reject
ineligible requests before durable activation. This guards against a regression
where rejecting HTTP status still masks a write in PostgreSQL or a provider
operation.

## Acceptance gates

The `jwt-security` CI job now compiles/runs the *real dependency-free Java core*
contract (not a mock generated by an LLM), then starts the real Spring Boot
resource server with PostgreSQL, RabbitMQ, and the independent SQLite provider.

It transmits eight malformed/unsupported raw HTTP requests and checks their
exact 400/413/415 statuses; verifies the ledger contains zero requests; probes
invalid routes/HTTP methods and scope boundaries (403); checks zero writes
again; and concurrently repeats the eight invalid inputs three times using
8 parallel clients (24 real requests), checking all HTTP statuses and no writes.
A later normal authorized request must still complete with signed evidence and
exactly one effect in the independent provider, as already required by the
existing harness.

The concurrency test is deliberately bounded. It is **not** an exhaustion,
load-limit, rate-limit, HTTP request-smuggling, or general penetration test.
It also does not establish that arbitrary invalid requests are rejected at
all reverse proxies or API gateways outside this Spring listener.

**Validation status:** Local JDK core contract and fixture suites passed before
commit; the new real Spring job will determine whether these checks actually
pass end to end.
