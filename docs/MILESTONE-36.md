# Milestone 36 — Full-byte reproducible source ZIP on independent runner

## Threat model

M32 and M33 ensure that every packaged file byte and executable mode matches the independent Git checkout; however, an attacker could still add harmless-looking ZIP comments, timestamps, noncanonical extra attributes or other wrapper bytes while keeping all source files untouched. Such a ZIP would pass content-only comparison but would not be the exact deterministic artifact generated by our producer.

## Implementation

The `--verify-reproducible` mode first performs the M33–M35 source, metadata and checkout validation, then invokes the package generator against its **own fresh checkout** in a temporary directory and compares the SHA-256 of the entire newly generated ZIP with the downloaded published ZIP. The CI consumer job uses this mode instead of the weaker content-only mode. The producer and verifier are pinned to Python 3.12, the same Git revision and the same OS runner family; differences in ZIP/zlib implementations outside those constraints can affect byte-level reproducibility and should be reviewed, not silently ignored.

The new offline regression tests prove that an untouched archive verifies across an independent rebuild, and that a ZIP with a modified comment still passes source file checks but fails canonical byte comparison.

## What it does not prove

This is independent **byte reproducibility** in two GitHub runners, not a cryptographic release signature, transparency-log proof, secure build attestation or physical independence from GitHub. A compromised Git commit and build workflow might produce the same malicious output in both places. No third-party packages are signed or verified by this change.
